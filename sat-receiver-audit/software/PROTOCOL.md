# UART-протокол SR-RX, версія 1

Цей документ описує формат повідомлення між хостом і Pico та API `srrx.wire`. Перевірка CRC виявляє пошкодження лінії: **вона не автентифікує джерело й не захищає від підробленого ARM**. Сесійний nonce видає Pico; це маркер поточного сеансу, не криптографічний ключ. Апаратні ворота E1–E5 і перевірка прошивки на реальному Pico залишаються окремими вимогами.

## Формат

```text
@<UTF-8 JSON>|<4 hex digits CRC16>\n
```

`@`, `|`, чотири цифри CRC та кінцевий LF є ASCII. JSON між ними кодується UTF-8. `\n` у прикладі означає один байт `0A`; CRLF не приймається. Переноси всередині JSON-рядків мають бути екрановані як `\\n`, а не передані сирим LF.

Максимальна довжина **всього** кадру — 512 байтів: один `@`, не більше 505 байтів JSON, один `|`, чотири hex-символи й один LF. Ліміт рахується в байтах, не в Unicode-символах. `@` та `|` усередині JSON-рядка дозволені; роздільником CRC є `|` безпосередньо перед останніми чотирма hex-символами.

CRC-16/CCITT-FALSE: ширина 16, polynomial `0x1021`, initial `0xFFFF`, RefIn/RefOut false, XorOut `0x0000`. CRC обчислюється **за точними переданими UTF-8 байтами JSON**, без `@`, `|`, hex CRC чи LF. Не розібрати JSON й не серіалізувати його повторно перед звіркою CRC: пробіли, порядок ключів та Unicode-екранування можуть відрізнятися. Перевірочний вектор `123456789` має CRC `29B1`.

Encoder випускає великі літери hex, decoder приймає великі та малі. Знаки, `0x`, пропущені чи зайві hex-цифри не допускаються. Компактний JSON encoder використовує `separators=(",", ":")`; побайтово канонічної серіалізації між CPython та MicroPython протокол не вимагає.

## Зовнішній об'єкт

Рівно п'ять полів, усі обов'язкові:

| Поле | Тип і допустиме значення |
|---|---|
| `v` | integer, тільки `1`; `true` та `1.0` не є версією 1 |
| `t` | string, один з `HELLO`, `HB`, `ARM`, `CONFIGURED`, `TRIP`, `SHUTDOWN`, `STATUS`, `EVENT` |
| `s` | unsigned integer `0..4294967295`, сесія; boolean не допускається |
| `q` | unsigned integer `0..4294967295`, номер послідовності; boolean не допускається |
| `p` | JSON object, вміст повідомлення |

Додаткові або відсутні зовнішні поля відхиляються. Повторення імені ключа відхиляється на будь-якому рівні JSON, зокрема коли `"p"` і `"\u0070"` позначають те саме ім'я. Це перевіряється до того, як JSON parser міг би перезаписати попереднє значення. NaN, Infinity, байтові об'єкти, tuple, нестрокові ключі й інші не-JSON значення не допускаються. UTF-8 перевіряється явно, включно з overlong-послідовностями, неповними символами, surrogate-кодовими точками й значеннями понад U+10FFFF.

Значення та обов'язкові ключі всередині `p`, дозволений напрямок кожного типу, heartbeat-пороги та переходи станів визначають відповідні host/Pico controllers. `wire.py` не видає дозволів на GPIO, не виконує ARM, не інтерпретує payload і не підтверджує закриття апаратних воріт.

## Сесія та послідовність

Pico видає поточний сесійний nonce. Controllers мають перевіряти відповідність `s` активному сеансу та дозволяти команди лише у відповідному стані. Номери `q` не обертаються: після `4294967295` потрібний новий сеанс/узгоджене повторне встановлення зв'язку. Controllers відхиляють повторені, застарілі та позасесійні повідомлення, а також перевіряють напрямок і payload перед дією.

**Decoder цих перевірок не робить.** Він навмисно поверне два синтаксично справні кадри з однаковим `q` або кадри з різними `s`: це дає контролерам можливість зафіксувати порушення та перейти у безпечний стан. Encoder лише перевіряє, що кожне окреме `s`/`q` входить у uint32, і не має прихованого лічильника.

## Heartbeat хоста та повторний TRIP

У hardware-режимі хост додає до `HB` поле `soc_temp_c`: найвищу температуру з `/sys/class/thermal/thermal_zone*/temp` у °C, з кроком 0,1 °C; зони читаються не частіше ніж раз на 1 s. Якщо будь-яку зону не прочитано або значення поза −40…130 °C, поле пропускається, і Pico тримає вентилятор увімкненим. У симуляції поля немає.

Після власного trip хост не надсилає `HB`, поки Pico звітує WARMING/CONFIGURING/ACTIVE для ARM, якого хост не веде. Замість HB він повторює `TRIP` не частіше ніж раз на 200 ms. Отже, один втрачений кадр TRIP не лишає Pico в ACTIVE: щонайпізніше через 750 ms без HB Pico сам утримує MCP RESET. Повторний звіт Pico про той самий TRIPPED/SHUTTING_DOWN/OFF у тому ж сеансі не є новою подією. Він не скасовує ARM, що вже в черзі, і не повторює запис all_off у MCP, які Pico тримає в RESET. ARM без підтвердження впродовж 1 s скасовується як `pico_arm_not_acknowledged`.

## API

```python
from srrx.wire import encode_frame, FrameDecoder

frame = {"v": 1, "t": "HB", "s": 42, "q": 7, "p": {}}
wire_bytes = encode_frame(frame)
decoder = FrameDecoder()
messages = decoder.feed(wire_bytes)
```

На Pico файл можна розгорнути як `wire.py` й імпортувати через `from wire import ...`. Модуль не залежить від `machine`, pyserial, dataclasses, typing або CPython `object_pairs_hook`. Він використовує `json`, а на старих збірках — fallback `ujson`.

| API | Поведінка |
|---|---|
| `encode_frame(frame) -> bytes` | Повертає кадр ≤512 байтів; хибні поля, непідтримувані JSON-значення, цикл або завеликий кадр дають `ValueError` |
| `FrameDecoder()` | Створює порожній decoder без сесійного стану |
| `.feed(data) -> list[dict]` | Приймає `bytes`, `bytearray`, byte-oriented `memoryview`; повертає всі справні кадри з цього виклику |
| `.feed(None)` | Порожній результат без помилки; підходить для UART timeout |
| `.feed(хибний тип)` | Порожній результат, збільшення `.errors`; не передавати text/string замість байтів |
| `.errors` | Кількість відкинутих кандидатів, oversize-кандидатів, неправильних аргументів і серій шуму; насичення на uint32 max |
| `.buffered_bytes` | Кількість утриманих байтів; завжди ≤511 |
| `.reset()` | Видаляє незакінчений кадр/стан шуму; зберігає накопичену `.errors` |
| `crc16_ccitt_false(data)` | Чиста функція CRC для діагностики й тестових векторів |

Фрагменти можна подавати по одному байту або довільними порціями; один `feed` може містити кілька кадрів. Порожні LF ігноруються. Шум до `@` відкидається; одна безперервна серія шуму рахується як одна помилка. При завершенні пошкодженого кандидата decoder також шукає придатний суфікс від пізнішого `@` в межах того самого обмеженого буфера. Так можна відновитися після обрізаного попереднього кадру без LF; `@` усередині справного payload не обнуляє його. Сумарна довжина перевірених суфіксів одного рядка обмежена 1024 байтами (2 × 512), тому CRC-робота на рядок лінійна: рядок із сотень `@` не зупинить цикл Pico до спрацювання WDT. Якщо в цьому бюджеті справного кадру немає, рядок відкидається.

При перевищенні 511 байтів до LF незакінчений кандидат відкидається й починається пошук нового `@`. Він не накопичується без обмеження. Помилки CRC, UTF-8, JSON та полів збільшують лічильник і не виходять як винятки декодування до контролера. Винятки `KeyboardInterrupt`/`SystemExit` не приховуються. Результат `feed` пропорційний кількості кадрів у переданій порції; адаптер має читати UART обмеженими порціями, наприклад до 128 байтів, та одразу обробляти список. Цей код не призначений для hard IRQ, де заборонене виділення пам'яті.

Зворотна сторона каналу також повинна враховувати короткий запис: `UART.write()` може повернути менше байтів або `None`; транспортний адаптер не може вважати такий кадр надісланим повністю. Це обов'язок UART adapter, а не `wire.py`.

## Перевірки та межа доказу

З кореня проєкту:

```bash
PYTHONPATH=software python3 -m unittest discover -s software/tests -p test_wire.py -v
```

Тести перевіряють еталон CRC, UTF-8, фрагментацію на кожній межі, з'єднані кадри, CRC-пошкодження, точну межу 512/513, oversized потік, повторні ключі/escaped aliases, boolean замість integer, невідомі версії/типи, невірний UTF-8/JSON, NaN/Infinity, відновлення після шуму, лінійну CRC-роботу пошуку суфікса та стабільну межу буфера. Окремий тест підтверджує, що replay/session policy залишається у controllers.

Host-тести не доводять випробування на фізичному Pico, синхронізацію UART під навантаженням, GPIO-поведінку або виконання heartbeat дедлайнів. До апаратного випуску потрібні перевірка на вибраній MicroPython-збірці та фізичні UART/timeout/noise тести.

Основні джерела сумісності: [MicroPython json](https://docs.micropython.org/en/latest/library/json.html) документує компактні separators та `loads`; [machine.UART](https://docs.micropython.org/en/latest/library/machine.UART.html) — часткове читання, `None` на timeout та результат `write`. Це документація development-гілки; сумісність із конкретною прошивкою підтверджується окремим запуском, а не самим посиланням.
